========================================
How do I write a target for my own host?
========================================

``ghr-pypi`` ships targets for a plain static host, Cloudflare Pages and nginx. If you deploy
somewhere else — Caddy, Fastly, an S3 bucket that wants a metadata manifest — you can add a
target without forking anything: write a small class in your own package, register it under
the ``ghr_pypi.targets`` entry point, and select it with ``--target``.

A target writes the files *your host* needs beside the index. It never touches the index
itself and never rewrites a URL — that is :ref:`config-assets`'s job — so there is very
little to get right. See :ref:`targets` for the full contract.

Write the target
================

A target is any object with a ``name`` attribute and an ``emit`` method. There is no base
class to inherit. This one writes a ``Caddyfile`` snippet for the finished site:

.. code-block:: python

   # your_package/targets.py
   from collections.abc import Sequence
   from pathlib import Path

   from ghr_pypi.targets import SiteContext, Target

   _SNIPPET = """\
   # Generated by ghr-pypi. Include this inside a site block.
   root * {root}
   file_server browse
   @metadata path *.metadata
   header @metadata Content-Type application/octet-stream
   """


   class CaddyTarget:
       """Writes a Caddyfile snippet for an index served by Caddy."""

       name = "caddy"

       def emit(self, site: SiteContext) -> Sequence[Path]:
           snippet = site.target_dir / "ghr-pypi.caddy"
           snippet.write_text(
               _SNIPPET.format(root=site.out_dir.resolve()), encoding="utf-8"
           )
           return [snippet]


   _check: Target = CaddyTarget()  # type-checked conformance; see "Type-check it"

Four things are doing real work here.

**The return value.** ``emit`` returns every path it wrote — a list, a tuple, any
:class:`~collections.abc.Sequence`. The command line echoes one line per path, which is what
makes an artifact landing outside the published site visible instead of a surprise. Returning
nothing is not an option: ``ghr-pypi`` rejects a non-sequence return with
``error: caddy target returned NoneType, expected a sequence of paths``. Return an empty
sequence when there is genuinely nothing to write.

**Not a generator.** Write the files, *then* return their paths. Yielding each path as you
write it would satisfy ``Iterable`` but not ``Sequence``, so a type checker rejects it — and
rightly, because it hands the moment a write can fail to whoever consumes the result instead
of keeping it inside your target. ``ghr-pypi``'s command line happens to materialize what you
return inside its own error handling, so a generator that slipped past type checking still
fails cleanly there; do not rely on that, because the next thing to call your target may not
be as careful.

**The directory.** This snippet goes to ``site.target_dir``, not ``site.out_dir``. Everything
under ``out_dir`` is published: a server configuration written there would be served to
anyone who can reach the index, and this one names the filesystem path the server roots at.
Use ``out_dir`` only for artifacts the *host* reads out of the deployed tree — Cloudflare
Pages' ``_headers`` is the built-in example. Everything a person reads goes in ``target_dir``.

**The ``_check`` line.** It does nothing at run time and exists purely so a type checker
compares ``CaddyTarget`` against the protocol. Nothing else in your package ever will: your
target is named in an entry point, which no checker reads. Leave it out and a wrong signature
sails past both mypy and pyright — see `Type-check it`_ below.

:class:`~ghr_pypi.targets.SiteContext` also carries ``projects``, ``title``, ``index_url``,
``assets`` and ``formats``, so a target can vary what it emits with what was built — the
built-in ``cloudflare`` target only writes its ``/files/*`` rules when ``site.assets`` is
``"mirror"``. Treat ``projects`` as read-only; a target that edited it would change what
every later reader sees, including an index that is already on disk.

Register it
===========

The entry point's name is the name you will pass to ``--target``. Its value must be a
**callable returning a target** — naming the class is the usual way, since calling a class
constructs an instance:

.. code-block:: toml

   # your_package/pyproject.toml
   [project.entry-points."ghr_pypi.targets"]
   caddy = "your_package.targets:CaddyTarget"

Pick a name that is not built in. ``static``, ``cloudflare`` and ``nginx`` always win a
collision, and your target would be ignored with a warning on stderr.

Install and run it
==================

Entry points are read from installed distributions, so an editable install is enough — but
the metadata is written at install time, so re-install after adding or renaming the entry
point:

.. code-block:: sh

   pip install -e .
   # or: uv pip install -e .

Then select it. Both forms work:

.. code-block:: sh

   ghr-pypi index yourorg/yourrepo --out site --target caddy
   ghr-pypi index yourorg/yourrepo --out site --target caddy --target-out ./deploy

.. code-block:: yaml

   # index.yml — with a config file, 'target' is a key, not a flag
   repositories:
     - yourorg/yourrepo
   target: caddy

.. code-block:: sh

   ghr-pypi index --config index.yml --out site --target-out ./deploy

``--target`` is refused alongside ``--config`` — it changes what the build produces, so the
file must be the whole description of it. ``--target-out`` is only a path, like ``--out``, so
it is accepted either way and defaults to the working directory.

A successful run reports each artifact:

.. code-block:: text

   wrote index for 2 project(s) to site
   wrote deploy/ghr-pypi.caddy for the caddy target

If the name is not registered, the run stops before the first network request and tells you
what is::

   error: unknown target 'caddy'; available: cloudflare, nginx, static

which almost always means the entry point was added without re-installing.

Type-check it
=============

``Target`` is ``@runtime_checkable``, so ``isinstance(CaddyTarget(), Target)`` is legal — and
close to worthless. A runtime-checkable protocol checks only that ``name`` and ``emit``
*exist*; their signatures and return types are not examined, so a target that takes the wrong
arguments or returns ``None`` passes.

Running a type checker does not fix that by itself. A class is compared against a protocol
only where it is assigned to one, and your target is only ever named in an entry point, which
no checker reads. Verified against this package's own toolchain: a class whose method is
``def emit(self) -> None`` — wrong parameters *and* wrong return — is reported clean by both
mypy and pyright.

The ``_check`` line in the example above is what makes the check happen:

.. code-block:: python

   _check: Target = CaddyTarget()   # type-checked conformance; isinstance cannot do this

With it, both checkers reject that class and name the mismatch. mypy's version reads::

   Expected:
       def emit(self, site: SiteContext) -> Sequence[Path]
   Got:
       def emit(self) -> None

pyright says the same thing in its own words. Keep the line, and run ``mypy`` or ``pyright``
over your package as part of its own tests.
